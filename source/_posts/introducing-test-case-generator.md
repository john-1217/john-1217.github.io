写测试用例大概是最适合交给大模型的活之一：输入是结构化程度不低的需求文档，输出是格式固定的用例表格，中间的「理解需求、拆分功能点、设计正常与异常分支」又正好是语言模型的强项。于是我把这套流程做成了一个开源项目 **test\_case\_generator**（FastAPI + LangGraph + Vue 3），本文记录一下它的思路和几个设计取舍。

<h2 id="what">它能做什么</h2>

-   上传 PDF / Word / Markdown 需求文档，自动解析正文、表格和图片
-   四阶段工作流：需求分析 → 测试策略 → 用例生成 → 覆盖总结
-   需求信息不足时进入「待澄清」状态，补充说明后继续执行，而不是硬编出用例
-   可关联知识库项目，检索业务规则注入生成上下文（RAG）
-   结果保存 Markdown 并导出 Excel，支持自定义用例模板字段
-   模型可配置：OpenAI / Gemini / DeepSeek / Kimi / OpenRouter 等，连接测试和模型管理都有界面

<h2 id="phases">为什么拆成四个阶段</h2>

一条 prompt 直接吐全部用例当然也能跑，但中间过程是黑盒。拆成四个阶段之后，每一阶段的产物都是独立可审计的：需求分析阶段暴露理解偏差，测试策略阶段可以人工调整范围，最后的覆盖总结能回答「这份需求到底测没测全」。配套的人机澄清（HITL）也是同一逻辑——与其让模型猜，不如让它提问。

<h2 id="kb">知识库与检索测试</h2>

生成用例时最缺的往往不是模型能力，而是业务规则：金额上限、时间限制、不同端上的行为差异，这些内容不在需求文档里，模型只能编。所以项目里做了知识库 RAG，把业务知识文档向量化后按需求模块检索注入。

为了验证知识本身的质量，我又做了个「检索测试页」：BM25 在浏览器内检索知识块，LLM 流式生成回答，每个结论带【n】引用编号，右侧能看到命中块的评分、章节路径和源文件。这个页面本身就是一次实践——先确保检索层可靠，生成层才有意义。

<h2 id="next">接下来</h2>

正在做用例质量评测：接入 LangSmith 的 Datasets 与 LLM-as-Judge，从需求点覆盖率、可执行性、冗余度几个维度给生成结果自动打分，改 prompt 或换模型后跑同一数据集直接对比实验结果。这部分跑通后再写一篇。

评测之外，还有一个正在规划的方向：知识图谱。最近读到一篇讲 [RAG + 知识图谱 + 智能体](https://developer.aliyun.com/article/1759748)的文章，观点和我做检索测试页时的体感一致——RAG 解决「找得到」，解决不了「连起来」：两个业务域的依赖关系隔着几十页文档，单靠相似度检索召不回来，生成的用例就永远缺一半。

结合我这边知识库的分层结构，可行的路径分三步：先用切块器解析出的文档层级、域归属和 L2 到 L3 的引用链，搭一张零成本的结构图谱；再从「下游交互说明」这类规则表里直接抽取依赖、触发和容错关系——这些表本来就是人工整理好的关系三元组；最后对核心域用 LLM 补文中叙述的隐式依赖。图谱不急着上 Neo4j，这个规模用 JSONL 邻接表就够。落地形态是双路召回（检索块 + 一跳子图合并进 prompt），再加一道生成后的覆盖自检：对照子图查漏，缺了自动补。

项目已开源：[github.com/john-1217/test\_case\_generator](https://github.com/john-1217/test_case_generator)，支持 Docker 一键部署，README 有完整的快速开始。欢迎试用和提 issue。
